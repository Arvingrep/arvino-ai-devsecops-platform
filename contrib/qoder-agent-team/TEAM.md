## 3. 注册准备、席位与真实权限

由后续获准的操作者先核查当前 Qoder 版本的自定义角色、团队、独立会话、模型选择和权限功能；未实查前不写死 UI 路径、成员上限或导入能力。文件是版本化指令源，不是已支持的一键导入包。若只允许总监加四个执行席位，按阶段调用独立角色/会话，释放完成的执行席位；无法保持 tester/security 独立时应阻塞，不能合并或让实现者代验收。

核查后可手工映射：frontmatter `name` 对应名称、`description` 对应说明，第二个 `---` 后正文对应工作指令，`tools` 仅作工具候选建议。默认模型字段**待实查、待配置**，不猜模型名称，不沿用历史模型事故条目作为当前可用性证据。

| 角色组 | 最小工具配置建议 | 执行边界 |
|---|---|---|
| lead | Read/Grep/Glob；管理记录 Edit/Write 按范围授权 | Bash 仅只读；若 UI 不能限定管理路径，则保持编辑需逐次确认 |
| architect/researcher/design | Read/Grep/Glob；researcher 可列 WebSearch/WebFetch 候选；规格/证据 Edit/Write 按范围授权 | 不改业务实现；公开资料只读访问限任务需要、现有工具及副作用核查范围，不默认开放网络或付费服务 |
| backend/frontend/devops/smartcontract | Read/Grep/Glob；任务路径 Edit/Write 按范围授权 | Bash 按命令确认副作用；合约动作按预算与安全审查执行 |
| tester/security | Read/Grep/Glob；隔离验证 Bash 按命令确认 | 不开放被测工作区编辑，不代修实现 |

这只是 UI 工具权限建议，**提示词不等于沙箱**；Bash、测试脚本及已有连接器仍可能写文件、访问网络或产生费用。注册前需核对实际工具白名单、文件范围、授权路径与副作用；不能隔离的动作保持阻塞，不声称已被强制禁止。不得为满足配置而扩大权限、改全局配置或新建付费连接。

独立验收必须同时满足：不同执行会话、没有参与被验实现、证据绑定同一候选版本，以及 tester/security 的模型家族分别 `different_from_implementer`。需另行实查候选实现者和验收者的真实模型家族、可用资格与成本，再在授权范围配置；默认同模型子 agent **不满足异构条件**，不同角色名或会话 ID 也不能证明异构。缺少可用且不新增付费的异构配置时记录模型阻塞，不擅自切换、调用探针或谎称满足。其他角色的模型由操作者实查后选择。

## 4. 业务入口、账本、唯一 owner

统一业务入口为各项目的 **GitHub Issue / Project**。需求、交付证据、待决策事项通过同一任务标识关联，具体写回或字段映射须核查任务授权。用户已授权的公开 GitHub Project 草稿卡记录是独立管理步骤；草稿不触发仓库 Issue，不证明真实 owner 或任务锁，也不是业务认领。本地配置编写者本轮不执行该网络步骤，不将草稿登记等同真实业务任务已接线。

已有 arvino 持久化账本可评估复用，**尚未接线**。先评估任务标识、owner、状态、阶段、版本、审批引用、审计事件及旧 Hermes 兼容性；不要新造一个聊天账本代替既有事实源。Qoder 会话仅是执行日志，不能作为业务主账、权威状态或真实任务锁。草案任务单、配置索引、聊天“已认领”均不是锁。

每个任务只有一个 owner；拆分的子任务有自己的唯一 owner，tester/security 核验作为独立子任务关联同一候选版本。同一仓库最多一个实现者并发写入（`max_parallel_implementers_per_repo: 1`）；只读评估可并行，跨仓库按依赖调度，不能由 frontend/backend/devops 同时改同一工作区。

firebird-sea 试点先进行**只读资格核查**：项目与仓库身份、Issue/Project 状态、现有 owner 与锁、旧 Hermes 排队/运行任务、权限与环境、工作区改动、验收命令副作用、模型与决策条件。记录核查时间及证据，但不在草案中假装占锁。只有核查完成、无竞争、真实账本认领接口及任务授权确认后，才可通过既有一致性/原子认领机制写入 owner；认领前再次确认状态，竞争或缺接口则阻塞。旧 Hermes 在交接验证完成前不关闭、不改其调度；无法证明无双调度时不执行实现任务。

## 5. 状态与阶段分离

| 状态 | 含义与迁移证据 |
|---|---|
| 待澄清 | 缺需求、范围或验收条件；补齐后才可待执行 |
| 待执行 | 条件齐备且尚未开始；真实认领及执行证据齐备后进入执行中 |
| 执行中 | owner 正在授权范围执行；候选产物与自测交接后待验证 |
| 待验证 | 等待独立 tester；Fast 按前置要求做必要 security，Standard/Governed 必经独立 security；核对同版本适用 CI/策略证据，失败进入返修 |
| 待发布 | 验证证据齐备，等待总监做发布决策；不自动发布 |
| 已交付 | 满足预先定义的交付条件且有证据；仅提交候选稿不能冒充上线 |
| 阻塞 | 条件无法满足，记录类别、证据、解除条件和恢复状态 |
| 返修 | 验收不通过，退回原 owner 修复；新版本重新验证 |
| 取消 | 有明确取消依据；保留原因与审计记录，不删除历史 |

`phase` 另记澄清/调研/设计/实现/自测/独立测试/安全核验/发布决策/发布准备/交付；不可把阶段当状态，也不从模型运行、会话结束或草案记录自动推导任务完成。阻塞和返修仍保留原阶段及版本，修复后按证据恢复。若本轮交付目标是文档候选稿，“已交付”只限该范围；上线与注册各自另验。

## 6. 前置验收与三档交接

总监在执行前定义：任务标识、唯一 owner、流程档位及理由、允许/禁止路径、输入与依赖、验收标准、候选版本标识、测试与安全要求、预算与环境限制、决策停止点、交付条件。需求不明先待澄清；实现者自测是交接条件，**developer 自测不等于独立验收**。三档均保留适用 CI、OPA 与已有策略门禁；文档型任务可在执行前明确适用性及不适用理由，但不得弱化代码交付基线，未执行项须如实记录。

- **Fast**：低风险小改动。总监先定义验收 → 对应实现者及自测 → 适用 CI/OPA/已有策略门禁 → 不同会话且异构条件满足的独立 tester → 必要 security → 总监汇总。Fast 不省略独立测试；鉴权、依赖、敏感数据、CI/IaC、合约等触发安全核验或升档。
- **Standard**：一般功能。总监澄清 → researcher/design 按需提供输入 → architect 固化方案与验收 → backend/frontend/devops 按仓库串行实现与自测 → CI/OPA/已有策略门禁 → 独立 tester **及 security** → 总监汇总并决策交付，不按风险跳过 security。
- **Governed**：架构边界、技术栈、基础设施、迁移、权限、合约、费用或发布风险。researcher/architect/design 形成证据与方案 → 总监定案并留证 → 对应实现者受控实现、自测 → CI/OPA/已有策略门禁 → 独立 tester **及 security** → 总监做发布决策并执行。方案与执行均由总监负责，不再逐动作请示；生产变更保留回滚与健康检查。

统一交接包：任务与 owner、范围、规格路径、候选 commit 或 image digest；未提交工作区使用可复核快照/diff 摘要与指纹，不能伪造 commit；改动文件、适用 CI/OPA/已有策略门禁结果及适用性理由、已执行命令/退出码/结果、未验证项、QA/安全证据、模型家族与会话证据、风险、回退方案及待决策动作。tester/security 核对同一候选版本和门禁结果，不修改被测实现、测试门禁或基线；允许在隔离副本中形成独立用例和脱敏证据，问题交回原实现者。

**代码交付须有实际 PR 链接及与 PR head SHA 一致的 CI、QA 和所需安全证据。** commit/push、开 PR、合并由团队按任务直接执行并留痕；不再存在“没有授权”的默认状态。未提交时的候选快照只用于中间评审，不能替代正式代码交付，也不得伪造 PR、SHA 或已通过门禁。

## 7. 决策、返修与阻塞

变更记录绑定：**具体动作、项目与目标环境、commit 或 image digest、QA 与安全证据、风险与回退、执行者与时间**。除唯一红线外，不需要 Arvin 逐条批准；总监对动作负责并留证。版本、image、目标环境、动作参数或风险证据变化后重新验证，不复用旧结论。发布不再默认停在“待审批”，由总监按门禁结果决定。

智能合约的编译/执行测试/模拟、RPC 读取或探针、签名、授权、部署、转账、升级等动作，由总监按任务目标与预算决策；执行前做只读方案、脱敏检查与模拟，记录链、环境、地址、版本、费用/资产影响、模拟证据与回退局限。唯一红线是不泄露私钥/助记词/密钥；真实签名与链上写不再需要逐动作人工批准，但必须留痕并在预算内。

同一错误签名的**3次同型失败**后停止重试，由总监升级处理；计数跨会话保留，不能换会话或角色清零。不同问题分开计数，修复必须提供新证据。遇到已知硬性条件缺失立即阻塞，不必空耗三次：

- 技术配置阻塞：工具、隔离、任务接线、依赖或执行配置缺失；交对应 owner 明确修复条件。
- 模型阻塞：实际资格、可用性、异构条件不满足；只报告，不猜名称或开付费模型。
- 凭据阻塞：授权缺失、失效或身份不符；仅请求安全授权途径，不索取/打印密钥。
- 人工决策阻塞：目标、预算或方向需要 Arvin 拍板；不把普通执行动作当作审批阻塞。

## 8. 试点验收与报告纪律

任务已授权的只读审计、静态审查与资格核查不需占用真实业务写任务锁，但仍须核查权限与副作用，不能借只读名义认领、写入或实施业务。firebird-sea 业务实现必须先满足注册资格（含模型与权限）、与 Hermes 无双调度、真实账本一致性认领及唯一 owner 锁条件，缺项即阻塞。业务端到端验收还须证明入口与账本关联、同仓库写入串行、前置验收、独立会话及异构模型条件、三档 CI/策略与测试安全交接、决策版本绑定、返修与阻塞可追踪；本地 YAML 解析不能替代这些验收。

总监仅在出现**有效新证据**时汇报：资格核查完成、真实认领成功、产物变化、独立验证结果、阻塞变化或待决策动作。没有新证据不定时刷屏，也不把子会话启动当业务进展。报告先结论，再给绝对产物路径、命令结果、证据与候选版本、未验证项、阻塞及需 Arvin 拍板的事项。

配置编写轮的离线自查范围（历史）：用已存在的 `.venv/bin/python`（不安装、不产生 pyc）解析 YAML/frontmatter，核对十个正式角色、索引路径及 legacy 标识，再执行 `git diff --check`。总监可另派静态审查，并在任务需要、现有工具可用且副作用核查通过的范围内进行轻量匿名端点只读验证（匿名 GET/有限跳转，不泄露私有资料）；该轮不包含登录、凭据/模型探针、安装或付费。上述自查、静态审查与匿名读取均不等于异构 QA、已验证登录、注册成功、生产变更或上线；配置编写者不自称独立验收者。
